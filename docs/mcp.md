# MCP server: plan routes from another agent

`bike-router mcp serve` lets any agent that speaks the [Model Context Protocol](https://modelcontextprotocol.io)
(Claude Desktop, Claude Code, an IDE, your own agent) plan bike routes with this service. It is a small
stdio server: the agent starts it as a subprocess, and it answers tool calls by asking a **running**
pyBikeRouter API. It adds no model and no new dependency.

```bash
bike-router mcp config --api http://127.0.0.1:8765     # prints the entry for the client's configuration
bike-router mcp serve  --api http://127.0.0.1:8765     # what the client runs (stdin/stdout)
```

`mcp config` prints, for example:

```json
{"mcpServers": {"bike-router": {"command": "bike-router",
                                "args": ["mcp", "serve", "--api", "http://127.0.0.1:8765"]}}}
```

Put that under `mcpServers` in the client's MCP configuration (for Claude Code: `claude mcp add bike-router
-- bike-router mcp serve --api http://127.0.0.1:8765`). `--api` defaults to `$BIKE_ROUTER_API_URL`, then
`http://127.0.0.1:8000`. The API must be reachable from where the client runs; it is the same service the web
page and the CLI use, so it needs the routing engine(s) and, for weather and sights, the same optional parts
(`/v1/capabilities` lists them).

## Install it without the repository

Once a release is on PyPI (see [Publishing](#publishing-to-pypi-and-the-mcp-registry)), a client can run the
server with no checkout and no install step, with [uv](https://docs.astral.sh/uv/):

```bash
BIKE_ROUTER_API_URL=http://127.0.0.1:8765 uvx bike-router mcp serve
```

The package is called like the command (`bike-router`), which is what `uvx` looks for. The server still needs a
**running pyBikeRouter API** to ask: the package is the thin client, not the routing engine; the API address comes from `BIKE_ROUTER_API_URL` or `--api`.

## The tools

| Tool | Does |
| --- | --- |
| `plan_route` | Plan a route between two places (names or `lat,lon`), or a loop (`loop` + `target_distance_km`), with `via`, bike type, surfaces, traffic and ferries, limits, departure time, alternatives, sight stops. Returns the best route and its alternatives as facts, and a **`plan_ref`**. An ambiguous place comes back as candidates with `lat,lon` to answer with. |
| `explain_route` | The facts of one route of a plan (`rank`, 1 = best fit): distance, duration, climb, surface and traffic shares, pros and cons against the best fit, warnings. |
| `route_weather` | The forecast along one route at its departure: temperature, rain, wind, daylight, a better departure when there is one; says so when there is no forecast. `detail=true` adds the hourly samples. |
| `sights_along_route` | Sights (or services: cafes, water, ...) along one route, best known first, with the distance from the route and the position along it. `categories`, `buffer_m`, `limit`. |

The server remembers the last 20 plans in memory, so a follow-up names a `plan_ref` instead of the agent
carrying a route's geometry around. A `plan_ref` is gone when the server restarts; plan again.

A `plan_route` answer looks like (shortened):

```json
{"status": "ready", "plan_ref": "plan-1", "explanation": "This 14.4 km route was generated by brouter ...",
 "route": {"rank": 1, "engine": "brouter", "profile": "custom_gravel-v2", "distance_km": 14.4,
           "duration_min": 34, "ascent_m": 29, "surface": "68 % paved, 18 % unknown, 13 % cobbles",
           "traffic": "15 % quiet streets, 85 % paths and tracks", "pros": ["..."], "cons": ["..."]},
 "alternatives": [{"rank": 2, "compared_with_best": "rank 2: ...", "...": "..."}],
 "files": {"gpx": "http://127.0.0.1:8765/v1/routes/....gpx", "geojson": "..."}, "notes": []}
```

Every tool result is both the text content (JSON) and `structuredContent`; a failure is a result with
`isError: true` and a message the agent can act on (an invalid argument names the problem, an unreachable API
says so, the API's own refusal is passed on). Only an unknown tool or a malformed request is a protocol error.

## What the tools guarantee

- **Facts only.** Every number is measured by the routing engine on its route, read from the OpenStreetMap
  tags along it, or forecast by a weather provider; every sentence is generated from those numbers by fixed
  rules, in the same words the web page and the chat use. No language model is involved and nothing is
  advice: no tool says a route is safe, and what is not measured is reported as unknown, never guessed (a
  surface that no tag describes stays "unknown", and is never counted as paved; a sight's fame that could
  not be looked up is missing, never "obscure").
- **Map text is data.** Names of places, streets and sights are text anybody can write into OpenStreetMap or
  Wikipedia. They come back in fields such as `places[].name` and every tool description says they are data,
  not instructions; an agent should treat them like any other web content.
- **Only the configured API.** The server talks to the `--api` address and nothing else: no tool takes a URL,
  a file path or a command. Arguments are checked against each tool's schema before anything is asked
  (unknown parameters are refused), and the API validates them again with the rules of `POST /v1/route/plan`.
- **Read-only.** The tools plan and look things up. They do not change settings, delete history or download
  map data. (A plan is recorded in the history when the API has a database, as for any plan.)

## Limits

- stdio only (a subprocess of the client); no HTTP transport, no authentication of its own: whoever can run
  the command can use the API it points at.
- Tools only: no MCP resources, prompts, sampling or logging. Requests are handled one at a time, and a plan
  can take from seconds to minutes (`--timeout`, default 300 s); cancellation notices are ignored.
- The protocol layer is written out in `mcp_server/protocol.py` (initialize with version negotiation for
  `2025-06-18`, `2025-03-26` and `2024-11-05`, `ping`, `tools/list`, `tools/call`) instead of using an SDK. It is
  tested against a real subprocess and a protocol-level client (`tests/mcp_server/`); it has not been exercised
  with every MCP host, so report a host that does not connect.
- Weather, sights and the number of alternatives depend on what the API has switched on and on the public
  services behind it (the public Overpass server is often overloaded: a sights call then answers with the
  API's 502 as a tool error).

## Publishing to PyPI and the MCP Registry

The [MCP Registry](https://modelcontextprotocol.io/registry/quickstart) (preview) lists MCP servers so that
clients can find them. It stores **metadata only**: the server must already be a package on PyPI, and the
entry says how to run it. Everything that can be prepared in the repository is:

| File | What it is |
| --- | --- |
| `server.json` | The registry entry: name `io.github.JonasHeinickeBio/bike-router`, description, repository, the PyPI package `bike-router` run with `uvx` as `mcp serve`, and the one environment variable (`BIKE_ROUTER_API_URL`). Validated against the registry's schema (`2025-12-11`). |
| `README.md` | Ends with a hidden `mcp-name: io.github.JonasHeinickeBio/bike-router`: PyPI shows the README as the package description, and the registry proves ownership by finding that string there. |
| `pyproject.toml` | PyPI metadata (keywords, classifiers, URLs); the package is named `bike-router`, like its command. |
| `.github/workflows/publish-pypi.yml` | Builds and uploads to PyPI when a `v*` tag is pushed, with PyPI trusted publishing (no token stored). |
| `scripts/check_release_version.py` | Run first by that workflow: the tag, `pyproject.toml`, `__version__` and both versions in `server.json` must be the same, or nothing is built. |

The version is written in those four places, so a release is: change them together, merge, then tag.

**What only you can do** (these use your own accounts; nothing here is done for you):

1. **Once, on PyPI:** create an account, then *Your projects > Publishing > Add a pending publisher*: PyPI project
   name `bike-router`, owner `JonasHeinickeBio`, repository `pyBikeRouter`, workflow
   `publish-pypi.yml`, environment `pypi`. In the GitHub repository create the environment `pypi`
   (Settings > Environments); requiring your approval there is a good guard.
2. **Each release:** bump the version (the four places), merge, then `git tag v0.3.0 && git push origin v0.3.0`.
   `release.yml` builds the container image and the easy-install zip, `publish-pypi.yml` uploads the package.
   Check <https://pypi.org/project/bike-router/>.
3. **Then the registry entry**, from a checkout of that tag:

   ```bash
   brew install mcp-publisher          # or the binary from github.com/modelcontextprotocol/registry/releases
   mcp-publisher login github          # a device code: you authorise it in the browser
   mcp-publisher publish               # reads server.json
   curl "https://registry.modelcontextprotocol.io/v0.1/servers?search=io.github.JonasHeinickeBio/bike-router"
   ```

   The login must be the GitHub account `JonasHeinickeBio`: with GitHub authentication a server name has to
   start with `io.github.<your login>/`. The publish fails with "Registry validation failed" until the PyPI
   package with the `mcp-name` string is live.

Publishing is public and cannot be fully taken back (a PyPI version number is never reused, and the registry is
a preview that may reset), so check the description in `server.json` (at most 100 characters) and the package
page before the first release.
